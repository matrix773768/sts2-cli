# M1-L3 CombatSolver 排序干预与搜索收益验证

2026-11-18。使用 M1-L2 的 `run_2 / OVERGROWTH_CRAWLERS` 及小战哨兵，测试局部调度优先级。环境为 Windows x64、STS2 v0.113.1 / Build 26660232、CoreCLR 9.0.7、上游 CombatSolver 0.51.5 源码 `78e4545e825e58c3d999354b1ffcd54241b1d2cf`。冻结原版 DLL SHA-256 沿用 M1-L2。隔离构建只用于离线 Harness。

## 竞争发生在哪里

| 阶段 | 职责与本例 |
| --- | --- |
| 生成与评分 | `Expansion` 从同父状态模拟动作和目标，`StateEvaluation` 根据预测快照生成分数。先防御 1,439,999，先打击战斗 ID 1 为 1,379,999。 |
| ActionCandidate 准入 | `Expansion.Candidates` 施加支配、分支上限、语义代表和有效伤害目标保护。防御与两个打击目标进入下游，结束回合另进入回合边界。 |
| 同池排序和全局保留 | `Prune → RankBest` 做去重、Beam 排序、必保和路由；其后追加资源等独立通道，再经 incumbent 及药水约束。M1-L2 在首个外层边界观测到防御与打击 ID 1 的 raw rank 为 0、2，选中名次也是 0、2，没有 required/routing 席位。三个出牌候选均进入最终列表，宽度 24 在此处无席位压力。 |
| 展开调度 | 阶段循环按 active 列表消费可展开父节点。调度还受转置、回合层配额、全局节点及时间边界约束。 |
| 终选与停止 | 原比较器使用完整胜利、资源及战损等质量轴。固定预算关闭达战损目标早停，仍允许前沿耗尽或预算终止。首胜可以用于收紧后续界，搜索仍可改善路线。 |

在原流程完成最终保留及 incumbent 检查后调整列表顺序。入口同时匹配 M1-L2 捕获的父状态指纹、两个子状态指纹、首步深度及动作和目标，只在同池首次同时命中时触发。A 为原版 DLL，另外跑带相同观测的 A 作为耗时对照。B 交换列表中的防御与打击 ID 1，C 请求防御优先，其位置原已领先。执行路径没有固定动作前缀。原始分数、保留名额、其他节点原位置、保留排名字段、原生状态、模拟 RNG 与路线终选均沿用原实现。小战用于检验指纹外的行为。

## 实验与复现

DOP 1，Beam 24，Smart 药水，无固定前缀。每个测量使用同配置预热一次。节点档为 400/1,200，另设 30 秒软上限。时间档使用 850 ms 软期限与 5,000 节点防护，三组交错次序；期限按原求解器检查点执行，实际结束可超出软期限。首胜时间为 Solve 内第一个提交或登记的完整无风险胜利，报告首胜展开、累计转移和时间，以及此后更低累计战损的见证。日志代价计入观测组搜索时间。进程单次限时 25 秒、批次 300 秒、托管堆硬限 256 MiB，原生复核截止 100 秒。

从同时包含 `sts2-cli` 和 `CombatSolver-m1-cs1` 的工作区运行。扫描宿主复用 M1-CS1 已构建 Harness，隔离源码复制到 `CombatSolver-m1-l3/patched-source`，构建需要该路径尚未存在。

```powershell
& sts2-cli/experiments/m1-l3/build.ps1
python -B sts2-cli/experiments/m1-l3/run.py CombatSolver-m1-l3/repro
python -B sts2-cli/experiments/m1-l3/verify.py CombatSolver-m1-l3/repro
```

## 固定节点结果

各行的战损为求解器累计战损。400 档返回部分前缀，真实完整战损未定义。1,200 档所有组终选完整动作一致，均先打击战斗 ID 1、零用药、第 9 回合击杀。

| 节点额度 / 配置 | 展开 / 转移 | 终选 | 首胜展开 / 转移 / Solve 时间 | 请求墙钟 |
| --- | ---: | --- | --- | ---: |
| 400 / A 原版 | 400 / 1,433 | 节点截断，前缀 23 HP | — | 827 ms |
| 400 / A 同观测 | 400 / 1,433 | 同上 | — | 1,554 ms |
| 400 / B 先打击 | 400 / 1,444 | 同上 | — | 1,742 ms |
| 400 / C 先防御 | 400 / 1,433 | 同上 | — | 1,804 ms |
| 1,200 / A 原版 | 757 / 2,463 | 胜，34 HP | 未采集 | 2,860 ms |
| 1,200 / A 同观测 | 757 / 2,463 | 同上 | 534 / 1,802 / 2,103 ms | 2,856 ms |
| 1,200 / B 先打击 | 759 / 2,470 | 同上 | 538 / 1,816 / 2,183 ms | 2,952 ms |
| 1,200 / C 先防御 | 757 / 2,463 | 同上 | 534 / 1,802 / 2,131 ms | 2,899 ms |

实际展开顺序从防御、打击 ID 2、打击 ID 1 改成打击 ID 1、打击 ID 2、防御。两候选的展开序号从 4 / 2 变成 2 / 4。观测的 12 次展开中，后续排列也发生变化。首次胜利为 46 HP 损失、第 7 回合。首次达到最终 34 HP 胜路的展开分别为 A 733、B 735、C 733。B 既未改善最终路线，也未节省达到同等质量的工作量。节点档每格只有一次热测，计时受机器负载与日志影响，尤其 400 档原版与同观测墙钟差异较大，不能估计排序代码的微秒级开销。节点和转移差异是更直接的成本证据。

## 固定时间结果

850 ms 软期限下各配置三次，5,000 节点上限均未触及。九次皆以 `TimeLimit` 返回部分路线，850 ms 内与返回时都未观测到完整胜利。墙钟高于配置期限，因为回合层只在检查点停止，且请求还要收尾。前缀战损随推进深度变化。

| 配置 | 胜利 / 样本 | 展开范围 | 转移范围 | 请求墙钟中位数（范围） | 前缀战损 |
| --- | ---: | ---: | ---: | ---: | ---: |
| A 同观测 | 0 / 3 | 131–158 | 719–849 | 1,280 ms（1,155–1,399） | 27–29 HP |
| B 先打击 | 0 / 3 | 158 | 849 | 1,247 ms（1,216–1,285） | 27 HP |
| C 先防御 | 0 / 3 | 104–158 | 581–849 | 1,134 ms（1,106–1,168） | 27–34 HP |

7 次走完 158 次展开并返回相同前缀。B 三次均达到这个边界，A、C 各一次提前终止。短时间档表现受离散检查点影响，且没有完整路线质量差异，不能据此确认 B 提高吞吐。时间档测量统一保留观测与干预开销，这组实验没有测到在线模型推理成本。

## 原生验证与决策

原版和带观测 A 在节点档的动作哈希、质量、展开、转移与边界完全一致。高档复现了 M1-L2 原版 757 展开、2,463 转移和 34 HP 的胜路。全部 19 项测量逐根匹配搜索根戳与 live 根戳。小战启用 B 没有匹配目标池，结果与原版一致，153 展开、423 转移、第 3 回合零损胜利。峰值工作集 178.3 MiB，无进程超时或不支持错误。

对 Crawlers 的唯一高档终选路线做了独立原生回放。29 步全部执行到卡牌奖励，第 9 回合结束，战后 52 HP（含燃烧之血的 6 HP 治疗），对应实际累计损失 34 HP。检查首步公开数值、各步出牌回合与终局。其余部分路线未做原生回放，这次也没有逐步比较完整内部状态。详见 [搜索记录](../experiments/m1-l3/results.json) 和 [原生见证](../experiments/m1-l3/native-results.json)。

**暂缓训练候选排序模型。** 这个局部次序干预确实改变展开，并能通过后续保留、转置及预算路径改变少量工作量。原版已经保有并找到低损胜路，提前展开它没有降低首胜或同质量胜路的展开数。400 档在首胜出现前已经截断。这些结果支持优先研究中后段状态评价、转移成本，以及困难战的完整胜路覆盖。本实验只识别一次首池调度操作的效果，尚未比较后续层的保留排序或席位调整，无法量化后续评价与保留机制各自的贡献。

定向验收包括隔离 Release 构建、固定预算对照、跨请求根戳比对、展开次序断言、原生回放和 `git diff --check`。正式求解器及 Steam 文件无改动。未运行全量 pytest 或五角色批次。
