最佳稳态样本达公开 Gate C 的 78.1%，中位达 77.6%（约 0.66 μs/step）。1,000 次预热的原版反汇编捕获到 `HotCombatEngine.Step` Tier 0。延长预热与关闭 tiering 两种措施独立改善同根吞吐，说明短进程的 JIT 编译阶段是主要已定位差距。剩余差距无法进一步分解为硬件、频率、JIT 代码差异或背景负载。

诊断版在正常 50,000 次计时之后另测逐段计数。三个复测的中位表观耗时为 Unpack 200 ns、Step 449 ns、Pack/规范化 325 ns、Hash 266 ns、状态值复制 196 ns，空时间戳约 26 ns。各段计时有测量扰动，合计值与原 Gate C 墙钟口径不同。每次验证 action 执行成功，Hash 与复制输入都有不变量 sink。Step 包含 Scratch 维护，未单独分离。该根 Cold Sidecar 为空，本轮不外推 Cold COW 开销。暂不修改内核。

## P3 · 六根 Coordinator 搜索

从原 24 世界按固定／复杂来源及 80／160／999 HP 取六个已冻结哨兵。所有试次主进程恢复默认可见 CPU 数，使用同一原版 Solver DLL。按根旋转 A–D 顺序，每臂单独冷启动、语义根比较和原生重放。请求 10 秒、固定预算、初始 Beam 96、配置节点 150,000，牌堆分支 18、手牌选择 24，禁药水，成长和额外遗物策略无目标。实测政策对象与进度日志逐次保存。Coordinator 把 32–63 的配置出牌分支解释为 64，因此 A/B 的有效分支相同。150,000 是配置档，匹配默认 profile 时 Coordinator 按阶段启用原生自适应策略，源码 Beam 为 96／240／320，救援可用 384，阶段节点档为 150k／320k／500k／650k。实测进度有扣除已用节点后的 317,072、490,011 报值，不能把快照的 150,000 当全请求硬上限。

## P5 · 优化前后与推荐

两个世界复测进程级 `DOTNET_TieredCompilation=0`。同行保持 DOP、策略、转移数、完整动作序列及冷启动原生净损一致。

| 世界及 DOP | 默认 → 无分层 JIT 求解秒 | 默认 → 无分层 JIT 冷启动加重放秒 | 原生净损 |
| --- | ---: | ---: | ---: |
| Haunted Ship，1 | 3.098 → 1.961 | 10.231 → 12.908 | 11 |
| Haunted Ship，4 | 1.966 → 1.484 | 9.204 → 12.511 | 11 |
| Soul Nexus，1 | 3.530 → 3.452 | 10.793 → 15.406 | 46 |
| Soul Nexus，4 | 3.075 → 2.038 | 10.000 → 13.783 | 46 |

关闭分层 JIT 加快求解调用，但冷启动额外编译使两根四组端到端均退化。禁用后的 Gate A 19/19 及 Gate B1 六角色 246 步均通过。保持默认 JIT，用 DOP=4 提速是当前实际完成的低风险优化，原生质量和相同工作量对照已验证。当前冷进程方案不应使用强制长预热或关闭分层 JIT 作为正式默认。

开销取样显示 DOP=4 版本，单次冷进程启动到稳定原生根及初始化字段的中位约 3.06 秒，胜路原生执行净时间中位约 249 ms。独立复放还需一次冷启动，六根的求解调用只占新宿主端到端的约 30%。编译、程序初始化、建根分别耗多少当前没有排他计数。现有搜索计时包含热根捕获、协调、路线物化和小量指标装配。JSON、RPC 和 SQLite 提交未做单项配对计时。Gate C 的两个原始 Harness 整体启动时间范围重叠，P3 的合成根与冷重放为 HK1A 适配独立增加的工序。常驻进程值得单独验证，需保持逐根彻底清理和冷验证身份。

**建议 DC3A 候选配置**维持现有合法性、目标、初始 Beam 96 与预算协议，使用默认 JIT、进程可见 CPU 至少 4、单 INF1 worker、DOP=4。出牌分支配置可写 64，使请求值与当前 Coordinator 有效值一致。先用已验证的 10 秒诊断点考察吞吐和质量，正式预算仍基于批准后的扩展证据。DOP=8 只在独占且确需额外吞吐时复核。现行冻结参考入口仍限制可见 CPU 为 1，本次候选仅在性能 Harness 启用。

**HK1B1 经验生产**优先测每 worker 常驻后稳定根、转移、公开投影／推断和入账的实际占比。保留默认 tiering，以真实合法牌和真实状态预热，分别量首根与稳态。经验生产关注并行 lane 的总吞吐，当前 Coordinator 的 DOP=4 收益不能直接用于多 lane 或 NOSL。先复用独立状态值和每 lane Scratch，并验证公开信息隔离及冷原生样本，再决定是否优化 Pack/Hash 和 Cold Sidecar。

## 复现与范围

证据目录 `logs/hk1a-perf/` 包括 `gate.json`、逐进程日志、环境与 DLL 身份、`jit-default.log`、阶段计时及 `search`、`fixed-nodes`、`legacy` 和 `no-tier-search`。逐根保留冻结配方、政策快照、求解输出及冷原生执行结果。诊断构建在新路径用 `experiments/hk1a/perf_overlay.py <输出> --archive ../hk0-isolated-131d10a/upstream.zip --steam <Steam根>`。用既有 DC3A Python 执行 `experiments/hk1a/perf_search.py <新输出> --build <诊断build.json>`。分别以 `--nodes 3000`、`--legacy`、`--no-tier` 重现有界补充对照。使用独立 Harness 产物执行原 Gate C，每个试次新起同一 .NET 9 宿主。进程 CPU 时间采集脚本及原始配置随本机结果保留。

剩余未验项目包括上游 Phase 0 完整复制、不同核心类型的定频比较、Cold Sidecar 工作负载、逐阶段排他剖析，以及更大根集的多线程端到端分布。未改动正式生产配置、求解内核或任何冻结任务。
