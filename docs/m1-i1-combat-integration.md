# M1-I1：CombatSolver 与 Headless 的最小战斗集成

2026-11-17。真实 Ironclad A0 跑局从 Neow 后地图进入普通三史莱姆战。CombatSolver 从当前原生战斗根求出 4 回合胜路；一个新进程恢复同一地图检查点，重进同一节点，**13/13 动作原生合法、逐动作状态零差异**。结算到卡牌奖励，跳过后回到地图。实验未改生产引擎、上游求解器或 Steam 文件。

## 架构与版本

sts2-cli 基线 `b478e0c2dd370cf1b4ecac9834d5531e72af6320`；STS2 v0.113.1 / Build 26660232，CoreCLR 9.0.7，Windows x64。CombatSolver 固定 0.51.5 / `78e4545e825e58c3d999354b1ffcd54241b1d2cf`，使用 CS1 原始 DLL（构建脚本校验 SHA-256），RitsuLib 0.6.14，兼容目标 0.113.0。

求解发生在隔离的 Headless 实验进程内：使用同一加载上下文、同一个 `sts2.dll`，从 `CombatManager` 取得当前 `CombatState`，交给 `CombatRootSnapshot.Capture`，再走离线宿主 Evaluate 使用的 `CombatBeamSolver.Solve` 单搜索入口。没有用 UI JSON、牌名数组或种子重建战斗，原生根直接提供卡牌实例、费用、动态变量、怪物状态及 RNG。复用上游 `Replay` 逐步生成预测帧、复用 CS4/CS5 的 `CaptureActual` 和 `CaptureSimulated` 作比较；没有改写求解算法。

原有 OfflineSearchHarness 有自己的游戏启动、存档及 Godot 适配，适合布置合成战斗，但没有经验证的通用 live-root 序列化入口。普通跑局存档也不能直接恢复任意战斗续体。跨进程重进地图节点可恢复本夹具，无需传送 CLR 对象；单独将当前战斗导入另一个求解器进程仍要重建或移植完整根及核对身份与 RNG。因而选择同进程捕获、跨进程执行验证，仅传计划与对账帧。

实验构建将 Headless 副本命名为 `OfflineSearchHarness`，使用上游现有友元访问。首次加载实测缺少 `STS2-RitsuLib.Runtime`；显式解析 RitsuLib 的 compat/shared 目录后可捕获根。之后显示名捕获缺少 `Node.FindChildren`，策略捕获缺少 `DisplayServer`，战损追踪需要初始化求解器日志。实验仅在复制的 GodotStubs 补空场景查询与 headless 显示名，并初始化本地日志；不启动完整模组生命周期或 UI。没有验证完整 RitsuLib 模组生态或任意 Godot 路径兼容。

## 调用及逐步原生差分

在仓库根运行。需要 CS1 基线 DLL、M1-B2 检查点及现有本地原生 DLL。可设置 `I1_RITSU` 指向本地 RitsuLib 根目录；`STS2_DOTNET` / `STS2_DOTNET_VERSION` 指定已安装的 CoreCLR 9.0.7 host。默认沿用前序实验的目录。

```powershell
python experiments/m1-i1/build.py
python -X utf8 experiments/m1-i1/run.py
```

1. 从固定 SHA-256 的 M1-B2 地图检查点加载 seed `m0-a-save-load-1`，选择 (2,1)。敌方 HP 为 11 / 27 / 14，玩家 80/80 HP、3 能量、99 金币，无药水。
2. 同一原生根冷搜和热搜各一次。两次动作、根及所有预测帧一致；捕获前后原生状态一致。第二进程重载同一检查点并重进节点，公开观察及原生根与参考一致。
3. 以牌 ID 和计划状态键内的出现序号绑定当前手牌索引；没有状态键时使用同 ID 出现序号。按目标 Combat ID 映射当前存活敌人索引，检查原生 `CanPlayTargeting`，再调用 Headless 原有出牌/结束回合动作入口。选择、药水、非法目标或回合不符都会停止。每步核对决策边界，最终击杀前安装的原生钩子在结算清理前捕获终态。
4. 10 次出牌、3 次结束回合全部匹配。每步按根中三个 Combat ID 比较双方 HP、能量、格挡、Power 及其内部状态、有序手牌和牌堆、费用与动态变量、敌方 AI、RNG 计数和精确续用戳。Shuffle 从 1 到 2，MonsterAi 从 1 到 5；覆盖敌人生成 Slimed、Vulnerable、敌人移除和跨回合洗牌。比较器所列字段通过，不构成原生对象图所有字段都相同的证明。
5. 三敌死亡，胜利锁定 HP 为 74；原生燃烧之血恢复至 80，金币 99 → 116，出现卡牌奖励，合法跳过后返回地图且保留 80 HP / 116 金币。奖励和结算检查原生行为，未与预测的奖励生成做差分。源检查点字节不变。

路线按目标 Combat ID 表示：T1 打击→2、防御、打击→2、结束；T2 痛击→2、打击→2、结束；T3 打击→1、打击→1、防御、结束；T4 痛击→3、打击→3。完整计划与状态在本地 `logs/m1-i1/trace.json`。比较失败时停止，留存首差步骤、动作前缀及期望/实际帧；动作失败则保留失败请求与引擎日志。夹具仅需该存档和上述地图分支即可重放，无需后续跑局。

## 成本与预算

最终配置 DOP 1、Beam 24、节点额度 1,000、分支额度 32/18/24；每次搜索软期限 6 s、8 s 取消令牌、命令最多等待 12 s，运行器请求合计截止 45 s（进程握手及回收另有各自超时）。每条路线最多 48 动作，CLR 托管堆硬上限 256 MiB；此限额不包含进程的原生内存。报告进程工作集高水位。数字为同一轮的单样本，不估计尾延迟。

| 阶段 | 实测 |
| --- | ---: |
| 求解进程握手 / 首次加载 / 进房 / 初次差分读根 | 1,457 / 2,655 / 201 / 144 ms |
| 冷捕获与求解 / 含预测逐动作帧及 IPC | 2,348 / 2,403 ms |
| 同根预热后捕获与求解 / 含预测逐动作帧及 IPC | 921 / 954 ms |
| 独立执行进程握手 / 加载 / 进房 / 初次差分读根 | 226 / 2,529 / 184 / 161 ms |
| 原生 13 步及逐步采样请求合计 / 跳过奖励 | 396 / 8 ms |
| 求解侧 / 执行侧峰值工作集（最后一次战斗采样） | 147.3 / 114.9 MiB |

这里的热样本复用已就绪进程与同一未动战斗根，未测跨房间或跨跑局热重置。定向验证为隔离构建和上述原生端到端断言。未跑全量 pytest 或五角色整局；实验未改变生产代码路径。

## 范围与正式接入前工作

当前只验证首个玩家回合、一个 Ironclad A0 普通战及无选择的出牌和结束回合。中途根、药水、特殊选择和续体、其它角色、精英、Boss、模组 Hook 以及更复杂的奖励尚未验收。正式接入前需要稳定版本化的桥接协议、覆盖更多真根与 A/B/A 隔离、支持显式选择与实例绑定、失败时交回原生策略、统一预算和取消回收，并验证永久资源、奖励及存档边界。

本实验有意使用完整隐藏 RNG，定位为离线 Teacher 和集成验证。正式在线 SL Agent 只能依据当前公开状态与在当前房间内合法试探获得的信息。这里的胜路不证明能在正常 SL 信息约束下在线获得同样结果。
