# M1-P1 原生常驻 Worker 与热恢复实验

在 Windows build 26200、CoreCLR 9.0.7、游戏 v0.113.1 / Steam Build 26660232 上，原生 worker 从已结算地图边界重新加载同一检查点，热恢复中位数为 **21.6 ms**。两轮 A→B→A 通过独立冷进程逐步差分。保留完整观察的批量协议将热房间推进从 **303.1 ms 降至 108.4 ms**，加上热恢复的分段合计为 **130.6 ms**。覆盖范围是 M1-B2 的两个固定分支，实验入口独立运行。

## 实验设计与等价结果

- 基线为 `cd03df4d954196364045be4695feae58a8c1c4da`。使用 [M1-B2](m1-b2-benchmark.md) 已有 Ironclad A0 检查点和两条 26 步脚本，起点在 Neow 后地图，脚本经原生地图选择及战斗抵达 `card_reward`。记录奖励后合法跳过选牌，推进到地图并写出当前存档。源检查点 SHA-256 为 `05c527152891c30807233fdfc4837ac2c4b0a6793fbedd600bc0c1ca6fea5295`，执行前后字节一致。
- 每轮依次用三个独立 PID 执行 A、B、A，再用单一 PID 对照。两轮共 6 个冷分支、6 个常驻逐步分支。首轮常驻通过后启动批量实验，另用两个 PID 各测 A→B→A，共 6 个批量分支。**12/12 常驻或批量分支等价**，共比较 312 个脚本动作的观察，另核对加载和奖励结算后的边界。10 个正常对照与实验进程均以 0 退出。
- 比较完整决策 JSON（含玩家资源、敌人、牌堆摘要和奖励）、每步完整地图、原生 `RunState.Rng` 与 `PlayerRng` 的可序列化状态。地图根与结算后另外比较原生跑局存档及 profile 进度。JSON 对象按键值比较，数组保留顺序。跑局存档仅去除墙钟字段 `save_time`、`run_time`，profile 仅去除独立进程随机生成的 `unique_id`。这些字段的原值仍在原始产物里。战斗中不生成回退存档，逐步 RNG 对照覆盖上述两个 RNG 集，额外的怪物或机制私有随机状态未单独枚举。
- 批量请求使用同一个动作路由和决策检测，逐步取完整决策、地图和 RNG，最多 64 条动作，遇到首个非 `combat_play` 决策停止。每条原脚本仍执行 26 步，返回同样的 `card_reward` 及逐步结果，奖励结算和存档检查仍走独立请求。由每步 3 次观测/动作往返合并成 1 次总请求；差分观测包含地图与独立 RNG 请求，不能直接套用到只发动作的客户端。

## 污染、清理与故障验证

第一版只做原生 `RunManager.CleanUp`、解除适配器事件订阅及更换 `RunSimulator`。热 B 所有外显决策、地图和 RNG 都与冷 B 一致，战后存档仍缺少 `players[0].discovered_enemies`，包括三种史莱姆。日志显示原生遭遇胜场和击杀累计为 2。A 和 B 是不同地图边，但在该根遇到同一怪组，因此触发了跨分支 profile 污染。实验保留了该失败，未过滤发现记录。修正是在首次挂载跑局前抓取当前隔离 profile 进度，清理后用原生序列化/反序列化创建新 `ProgressState`，再加载同一不可变检查点。修正后原生跑局存档和 profile 都通过差分。

重置限已结算的地图状态。检查战斗及执行器空闲、同步队列空、无待决选牌/奖励/礼包、无未成功完成的事件或商店任务、无回合超时或 Yield 抑制残留。先解除本适配器注册的两个战斗回调，释放 selector scope，再调用原生清理并再次检查空闲，最后清除静态礼包引用、销毁事件信号和替换适配器。模型库等只读或一次性设施保持热态。托管后台任务、其他原生静态缓存与长期内存仍需独立实证；这里的空闲检查只是受测边界的准入条件。

四种故障均由实验客户端终止进程，退出码为 1，后续没有复用。覆盖非法动作、注入加载观察不一致、250 ms 请求超时，以及用辅助入口构造 `WOOD_CARVINGS` 真正挂起 `card_select` 后尝试重置。额外事件仅用于验证待决续体拒绝及丢弃，未纳入速度样本。两组固定战斗验证了正常奖励结算后的可重置性，事件续体完成后的复用和原生死亡/胜利终局尚未覆盖。

## 下一阶段

**优先试验把批量固定脚本的决策边界判断与富观察构造分开。** 在同一动作入口保留原生行为、选牌/奖励产生和停止条件，先用审计模式逐步生成原观察做差分，再让固定脚本只在边界或必要时构造和传回富观察。两条脚本分别核对动作合法性、完整审计轨迹、RNG 和结算存档，并分别计量原生构造及序列化。热批量仍有约 36.5 ms 决策构造和约 44.2 ms 动作区间，完整恢复加推进的观察最小值约 122.5 ms。100 ms 或可通过减少这两类工作逼近，10 ms 低于本次所有热恢复样本，现有证据不足。扩展为通用 worker 前仍需证明更多房间、失败分支及长生命周期的隔离。

## 复现与验证

在仓库根使用 SDK 10.0.404、已有本地游戏 DLL 和 CoreCLR 9.0.7。按环境配置 `STS2_DOTNET`、`STS2_DOTNET_VERSION=9.0.7`，需要时设置工作区内的 `DOTNET_CLI_HOME` 和 `NUGET_PACKAGES`。保留历史 M1-B2 的 `summary.json` 与匹配检查点。

```powershell
python scripts/m1_p1/build_probe.py
$checkpoint = (Get-ChildItem logs/m1-b2-benchmark/checkpoints/*.save).FullName
python scripts/m1_p1/run_probe.py logs/m1-b2-benchmark/summary.json $checkpoint logs/m1-p1/repro
```

独立构建在 `logs/m1-p1/build`。正式产物为 `logs/m1-p1/final/results.json`、逐步观测、存档与子进程日志，失败对照在 `trial-1` 至 `trial-4`。正式探针 DLL SHA-256 为 `6365481915ebeb3e7bfd61b0984102d4e84416c8bcbab78b4ed0a22fc369eed6`，原生游戏 DLL SHA-256 与 M1-B2 相同。独立构建成功，有 GodotStubs 既有 C# 警告及 NuGet 审计源不可访问警告。运行器通过上述对照和故障验证，生产引擎/调度器源码未修改，未跑全量 pytest 或五角色批次。
